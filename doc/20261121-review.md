# 20261121 レビュー: LSP 仕様適合テストの失敗と修正方法

## 1. 背景

`tests/UnityCSharpFastLSP.Tests/Spec/` に LSP 仕様適合テストを追加した（120 ケース）。
リポジトリは `global.json` の SDK 11.0.100 が環境に無いためビルドできない。
そこで `net11.0` を `net10.0` に差し替えたコピーでビルド・実行した。

結果: 161 件中 153 件成功、8 件失敗。失敗はいずれもサーバー実装が仕様から外れていることを示す。

本ドキュメントは 8 件の失敗ごとに、原因・該当コード・修正方法・確認条件をまとめる。
修正そのものはこのドキュメントの作成時点では行わない。

## 3. 修正方法

### 3.1 JSON-RPC の応答（#1〜#5）: `src/UnityCSharpFastLSP.Server/LspServer.cs`

**エラー応答の書き出し**

`LspMessageWriter` には `WriteError(object? id, int code, string message)` と `JsonRpcErrorCode` 定数（`ParseError`, `InvalidRequest`, `MethodNotFound`, `InternalError`, `ServerNotInitialized`）が既にある。
新しく同等の関数を作らず、これを使う。

**`HandleMessage` の分割**

現状は `using JsonDocument doc = JsonDocument.Parse(message);` が例外を投げると、`HandleMessage` の外に例外が漏れる（#4, #5）。

修正:

1. `HandleMessage` で `JsonDocument.Parse` を `try` で囲み、`JsonException` を捕まえる。
   - `_writer.WriteError(null, JsonRpcErrorCode.ParseError, "Parse error")` を返し、`return true;` する。
2. ルート要素が Object でない場合（例: `[1]`）は `InvalidRequest` を返す。
3. 残りの処理を `private bool Dispatch(JsonElement root)` に移す。

**初期化ゲートと shutdown ゲート（#2, #3）**

`Dispatch` の先頭で、`id` を持つリクエストに対して次を判定する（通知は対象外）。

- `method` が `initialize` でも `shutdown` でもなく、`_isInitialized == false` → `ServerNotInitialized`（`-32002`）
- `_isShutdown == true` → `InvalidRequest`（`-32600`）

`_isInitialized` は `case "initialize"` の `HandleInitialize` の後で `true` にする。

**未知のリクエスト（#1）**

`switch` の `default` を変更する。

- `id` がある場合: `_writer.WriteError(id, JsonRpcErrorCode.MethodNotFound, $"Method not found: {method}")`
- `id` がない（通知）場合: 何も書かない（現状どおり）

**ハンドラ内の例外**

`catch` 内の `WriteRawResponse(id, "null"u8...)` を `WriteError(id, JsonRpcErrorCode.InternalError, "Internal error")` に変える。

**注意**

- `shutdown` は初期化前でも受け付ける（LSP の挙動に合わせる）。
- `exit` は現状どおり `HandleMessage` が `false` を返す。
- `initialized` 通知は現状どおり何も返さない。

### 3.2 references の `includeDeclaration=false`（#6）: `src/UnityCSharpFastLSP.Semantics/ScopedResolver.cs`

**原因**

`ResolveReferences` は `includeDeclaration=false` のときも、テキスト走査で宣言位置を拾ってしまう。

**修正**

1. 宣言位置の集合を作る。
   - `model.Index.FindDefinitions(word)` の結果
   - `ResolveScopedDefinition(model, uri, position)` の結果（ローカル変数・パラメータは索引に無いため必要）
   - 両方のうち、同じ URI（`UriHelper.Normalize` で比較）のものの `Range.Start` を `HashSet<(int Line, int Character)>` に入れる。
2. テキスト走査で、開始位置がこの集合に含まれる出現は `refs` に入れない。
   - `includeDeclaration=true` のときは集合を空にしておくので、現状の挙動は変わらない。

**確認**

- `References_IncludeDeclarationFalse_ExcludesDeclarationLine` が通ること。
- `includeDeclaration=true` の既存テスト（`References_IncludeDeclarationTrue_ContainsDeclarationLine` など）が壊れないこと。

### 3.3 formatting（#7, #8）: `src/UnityCSharpFastLSP.Syntax/FastFormatter.cs`

**編集範囲（#7）**

現状: `lastLine = lines.Length`, `lastChar = lines[^1].Length`。
末尾が改行で終わる文書では `lines` の最後が空文字列なので、終端行が文書の行数と同じ（存在しない行）になる。

修正: 終端を文書内の最終行にする。

```csharp
int lastLine = lines.Length - 1;
int lastChar = lines[^1].Length;
```

**改行コード（#8）**

現状: `sb.AppendLine()` と最後の `+ Environment.NewLine` を使うため、Windows では LF の文書に CRLF が入る。

修正:

1. 文書に `"\r\n"` が含まれるかで改行を決める。
   ```csharp
   string eol = source.Contains("\r\n") ? "\r\n" : "\n";
   ```
2. `sb.AppendLine()` → `sb.Append(eol)`、`sb.AppendLine(line)` → `sb.Append(line).Append(eol)`。
3. 最後の `+ Environment.NewLine` → `+ eol`。

**注意**

- 現状の整形は文書全体を 1 つの `TextEdit` で置き換える。内容が変わらなくても編集を返す。テストは「適用後の文書が変わらないこと」で判定しているので、この挙動は問題にしない。

## 5. 確認手順

リポジトリは `global.json` の SDK 11 が無いため、コピーを作って `net10.0` に差し替えて実行する。

```powershell
$dst = "$env:TEMP\verify-lsp"
if (Test-Path $dst) { Remove-Item -Recurse -Force $dst }
robocopy "D:\wsgit\UnityCSharpFastLSP" $dst /E /XD obj bin .git artifacts benchmarks vendor .hancho /NFL /NDL /NJH /NJS /NP | Out-Null
Get-ChildItem -Path $dst -Recurse -Include *.props,*.csproj,*.fsproj | ForEach-Object {
    $c = Get-Content $_.FullName -Raw
    if ($c -match 'net11\.0') { ($c -replace 'net11\.0','net10.0') | Set-Content -Path $_.FullName -Encoding utf8 }
}
Remove-Item (Join-Path $dst "global.json") -Force
Set-Location $dst
dotnet test tests\UnityCSharpFastLSP.Tests\UnityCSharpFastLSP.Tests.csproj
```

期待結果: 161 件すべて成功。
